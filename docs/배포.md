# 배포와 설치 안내

앱 소개와 사용법은 [README](../README.md)와 [메뉴별 안내](guide/)에 있다.
이 문서는 빌드하고 내보내는 사람을 위한 것이다.

## 배포처(빌드 종류)

코드는 하나이고, 새 버전을 받는 길만 배포처마다 다르다. 빌드 종류(store)로 나눈다.

| 빌드 | 배포처 | 새 버전 | 배포처에만 있는 코드 |
| --- | --- | --- | --- |
| `github` | GitHub Releases 의 APK | 앱이 GitHub 에 묻고 APK 를 받아 직접 설치한다 | `app/src/github` (업데이터, 인터넷·설치 권한, 설치 결과 수신기) |
| `play` | Google Play 내부 테스트 | Play 인앱 업데이트. 받기와 설치는 Play 스토어가 한다 | `app/src/play` (인앱 업데이트) |

- Play 는 스토어 밖에서 스스로 업데이트하는 코드와 설치 권한(`REQUEST_INSTALL_PACKAGES`)을 금지한다. 그래서 그런 것은 모두 `app/src/github` 에만 두고, `play` 빌드에는 들어가지 않는다. 인터넷 권한도 `play` 에는 없다.
- applicationId(`com.dong.budget`)·버전·서명키는 두 빌드가 같다. GitHub 에서 받은 앱을 지우지 않고 Play 버전으로 덮어 설치할 수 있다(반대도 된다).
- 공통 화면은 `AppUpdates` 로만 새 버전을 본다. 배포처마다 같은 이름으로 하나씩 두는 것은 `AppUpdates.kt` 머리말에 적어 두었다.
- Android Studio 의 기본 빌드는 `githubDebug` 다. Build Variants 창에서 바꾼다.

## 로컬 빌드

```bash
./gradlew assembleGithubDebug      # 디버그 빌드 (GitHub 배포)
./gradlew assemblePlayDebug        # 디버그 빌드 (Play 배포)
./gradlew installGithubDebug       # 연결된 기기에 설치 (installPlayDebug 도 같다)
./gradlew spotlessApply            # 코드 포맷 정리
./gradlew lintGithubDebug lintPlayDebug   # 린트
```

`assembleDebug` 는 두 빌드를 모두 만든다. `testDebugUnitTest`·`lintDebug` 처럼 빌드 종류가 빠진 이름은 이제 없다.

두 디버그 빌드는 같은 디버그 키로 서명돼서 서로 덮어 설치할 수 있고, 기기의 가계부는 그대로 남는다.
`play` 디버그 빌드는 Play 스토어에서 설치한 것이 아니라서 앱 정보에 'Play 스토어에서 설치한 앱에서만 업데이트를 확인할 수 있어요'가 보인다.
Play 인앱 업데이트는 Play 에서 받은 앱(내부 테스트 등)에서만 확인할 수 있다.

`local.properties` 에 Android SDK 경로가 있어야 한다. 없으면 만든다.

```
sdk.dir=/Users/<이름>/Library/Android/sdk
```

### 테스트

```bash
./gradlew testGithubDebugUnitTest testPlayDebugUnitTest   # 단위 테스트. 배포 때 GitHub Actions 도 돌린다
```

배포처에만 있는 코드의 테스트는 `app/src/testGithub`, `app/src/testPlay` 에 있다.

그대로 돌리면 공통 테스트(`app/src/test`)가 두 빌드에서 두 번 돌고, 혼자 6분 넘게 걸리는 고정지출 시뮬레이션
(`FixedExpenseSimulationTest`)도 두 번 돈다. 빠르게 돌리려면 속성을 준다(`app/build.gradle.kts`).

```bash
# 공통 테스트는 github 빌드에서 한 번만, play 빌드는 play 전용 테스트만
./gradlew testGithubDebugUnitTest testPlayDebugUnitTest -Pdongbudget.flavorTestsOnly
# 고정지출 시뮬레이션까지 빼면 1분이 안 걸린다(고정지출 계산을 고쳤으면 빼지 말 것)
./gradlew testGithubDebugUnitTest testPlayDebugUnitTest -Pdongbudget.flavorTestsOnly -Pdongbudget.skipSlowTests
```

빌드 검사(main 푸시)는 `flavorTestsOnly` 로 돌고 시뮬레이션은 늘 돌린다. 배포(태그)는 지난 배포 뒤로 시뮬레이션이 보는 코드가
안 바뀌었으면 시뮬레이션을 건너뛴다(`.github/workflows/release.yml` 의 경로 목록).

DB 마이그레이션 테스트는 실제 SQLite 에서 돌아야 해서 기기(에뮬레이터)에서 돌린다.
DB 버전을 올리거나 마이그레이션을 고쳤으면 배포 전에 한 번 돌린다.

`./gradlew connectedGithubDebugAndroidTest`(`connectedPlayDebugAndroidTest`, `connectedAndroidTest` 도 같다)는 **쓰지 않는다**. 끝나고 앱을 지워서 그 기기의 가계부가 사라진다.
대신 APK 를 덮어 설치하고 직접 실행한다.

```bash
./gradlew assembleGithubDebug assembleGithubDebugAndroidTest
adb install -r app/build/outputs/apk/github/debug/app-github-debug.apk
adb install -r app/build/outputs/apk/androidTest/github/debug/app-github-debug-androidTest.apk
adb shell am instrument -w com.dong.budget.test/androidx.test.runner.AndroidJUnitRunner
```

테스트는 별도 이름의 DB 를 쓰므로 기기에 있는 가계부는 건드리지 않는다.

## 배포

### 1. 서명키 만들기 (딱 한 번)

**이 키는 절대 잃어버리면 안 된다.** 키가 바뀌면 두 가지가 동시에 깨진다.

1. 기존 사용자가 업데이트를 설치할 수 없다 (앱을 지우고 다시 깔아야 하고, 그러면 가계부 데이터가 전부 사라진다)
2. Android 자동 백업 복원이 실패한다

Play 배포도 이 키로 서명한다([Play 배포](#play-배포) 참고). Google 이 새로 만든 키를 쓰면 GitHub 에서 받은 앱 위에 Play 버전을 설치할 수 없다.

저장소 바깥에 만들고, 만든 뒤 별도 장소에 백업한다.

```bash
keytool -genkeypair -v -keystore ~/dong-budget-release.jks \
  -alias dong-budget -keyalg RSA -keysize 2048 -validity 10000
```

비밀번호를 물어보면 직접 정해서 넣는다. 그 비밀번호도 키와 함께 안전한 곳에 적어둔다.

로컬에서 서명된 빌드를 만들려면 `keystore.properties.example` 을 `keystore.properties` 로
복사하고 값을 채운다. 이 파일과 `.jks` 는 `.gitignore` 에 걸려 있어 커밋되지 않는다.

### 2. GitHub Secrets 등록

저장소 Settings → Secrets and variables → Actions 에서 네 개를 만든다.

| 이름 | 값 |
| --- | --- |
| `KEYSTORE_BASE64` | `base64 -i ~/dong-budget-release.jks \| pbcopy` 결과 |
| `KEYSTORE_PASSWORD` | 키 저장소 비밀번호 |
| `KEY_ALIAS` | `dong-budget` |
| `KEY_PASSWORD` | 키 비밀번호 |

### 3. 새 버전 내보내기

`gradle.properties` 에서 두 값을 올린다. `versionCode` 는 반드시 커져야 한다.
낮추거나 같으면 기기가 설치를 거부한다.

```properties
dongbudget.versionCode=2
dongbudget.versionName=1.0.1
```

로컬에서 APK 를 직접 뽑으려면 다음을 쓴다.
Android Studio 의 Generate Signed APK 대화상자 대신 이걸 쓰는 이유는,
GitHub Actions 가 타는 것과 완전히 같은 경로라서 결과가 어긋나지 않기 때문이다.

```bash
./scripts/release.sh           # GitHub 배포용 APK (dong-budget-버전.apk)
./scripts/release.sh --play    # Play 배포용 AAB (dong-budget-버전.aab) 도 같은 키로 함께
```

직접 Gradle 로 만들면 `./gradlew assembleGithubRelease`(APK), `./gradlew bundlePlayRelease`(AAB)다.
결과는 `app/build/outputs/apk/github/release/`, `app/build/outputs/bundle/playRelease/` 에 나온다.

처음 한 번 `.signing-fingerprint` 에 서명키 지문을 기록해 두면,
다음부터 다른 키로 빌드하려 할 때 배포 전에 막아준다.
이 파일은 비밀이 아니므로 저장소에 커밋한다.

커밋하고 같은 이름으로 **메시지가 있는 태그(-a)** 를 만들어 올린다.
태그 메시지가 GitHub 배포 본문과 앱의 업데이트 화면·패치노트에 '바뀐 점'으로 그대로 보인다.
메시지 없는 태그(`git tag v1.0.1`)로 올리면 앱에 바뀐 점이 비어 보인다.

태그 메시지는 앱 패치노트(`ui/patchnotes/PatchNotes.kt`)의 그 버전 내용을 그대로 옮긴다.
메뉴마다 `[메뉴 이름]` 한 줄, 그 아래 항목을 `- 종류: 내용` 으로 적는다. 종류는 추가 → 개선 → 수정 → 오류수정 순서다.
메뉴 이름에 `#` 을 쓰지 않는다. git 이 태그 메시지에서 `#` 으로 시작하는 줄을 주석으로 보고 지운다.
업데이트 화면은 앞의 6줄만 보여주고, 전체는 패치노트에서 보인다.

```bash
git tag -a v1.0.1 -F - <<'EOF'
[거래 등록]
- 추가: 바뀐 점 하나
- 오류수정: 바뀐 점 둘

[설정]
- 개선: 바뀐 점 셋
EOF
git push origin main v1.0.1
```

태그를 올리면 GitHub Actions 가 두 빌드의 단위 테스트를 돌리고, 서명된 APK 를 만들어 Releases 에 올린다.
태그와 `versionName` 이 다르거나, `versionCode` 가 이전 배포보다 크지 않거나, 테스트가 실패하거나,
APK·AAB 의 서명키가 `.signing-fingerprint` 와 다르면 배포하지 않는다.

같은 실행이 Play 배포용 AAB 도 만든다. AAB 는 Releases 에 올리지 않고(앱 내 업데이터가 `.apk` 만 찾게)
실행 화면 아래의 결과물(Artifacts) `dong-budget-v버전-play-aab` 로 남긴다.
Play 에 올리는 것은 Releases 에 올린 뒤에 하므로 Play 쪽 문제로 GitHub 배포가 막히지 않는다([Play 배포](#play-배포)).

### 저장소는 공개여야 한다

비공개 저장소는 Releases 첨부파일을 받을 때 인증을 요구한다.
앱이 인증하려면 토큰을 APK 에 넣어야 하는데 APK 는 뜯어볼 수 있어서 토큰이 그대로 새어나간다.

가계부 데이터는 기기 안에만 있고 저장소에는 코드만 올라간다.
서명키도 저장소가 아니라 Secrets 에 있으므로 공개해도 안전하다.

## Play 배포

Play 스토어의 **내부 테스트** 트랙으로만 내보낸다. 처음 한 번은 Play Console 에서 손으로 해야 하는 일이 있다.

### 1. 앱 서명 키 (첫 버전을 올리기 전에)

Play 는 올린 AAB 에서 기기별 APK 를 만들어 Play 의 앱 서명 키로 서명한다(Play App Signing).
이 키가 지금의 서명키와 다르면 GitHub 에서 받은 앱 위에 Play 버전을 설치할 수 없다(서명이 달라 지우고 다시 깔아야 하고, 가계부가 사라진다).

- 첫 버전을 올리기 **전에** 앱 서명 설정에서 Google 이 새 키를 만들게 두지 말고, **기존 키를 내보내 올리는 방법**(Play Console 이 안내하는 PEPK 도구)으로 지금의 서명키를 올린다.
- 한 번 정한 앱 서명 키는 바꿀 수 없다고 보고 신중히 한다.
- AAB 도 같은 키로 서명해 올리므로 업로드 키도 같은 키다.

### 2. 첫 AAB 는 손으로 올린다

Play API 는 앱의 첫 버전을 만들 수 없다. 그래서 첫 AAB 는 Play Console > 테스트 > 내부 테스트에서 직접 올린다.

- 태그 배포 실행의 결과물 `dong-budget-v버전-play-aab` 를 받거나, 로컬에서 `./scripts/release.sh --play` 로 만든다.
- 테스터(이메일 목록)를 넣고 내부 테스트를 내보낸다. 테스터는 초대 링크로 참여한 뒤 Play 스토어에서 설치한다.
- `versionCode` 는 GitHub 배포와 같은 값을 쓴다. Play 는 한 번 올린 `versionCode` 를 다시 받지 않으므로 손으로 올린 버전보다 큰 버전부터 자동으로 올라간다.

### 3. 자동 업로드 켜기

태그를 올릴 때 Actions 가 AAB 를 내부 테스트에 바로 내보내게(completed) 하려면 둘 다 있어야 한다.
하나라도 없으면 Play 에는 올리지 않는다(변수를 켰는데 시크릿이 없으면 실패로 알린다).

| 종류 | 이름 | 값 | 넣는 곳 |
| --- | --- | --- | --- |
| 시크릿 | `PLAY_SERVICE_ACCOUNT_JSON` | 서비스 계정 키(JSON) 파일 내용 전체 | Settings → Secrets and variables → Actions → Secrets |
| 변수 | `PLAY_UPLOAD_ENABLED` | `true` | Settings → Secrets and variables → Actions → Variables |

- 서비스 계정은 Google Cloud 에서 만들고 키(JSON)를 받은 뒤, Play Console > 사용자 및 권한에서 이 앱의 테스트 트랙에 출시할 수 있는 권한을 준다.
- `PLAY_UPLOAD_ENABLED` 는 **2번의 첫 손 업로드를 마친 뒤에** 켠다. 켜기 전에 태그를 올리면 Play 에 앱이 아직 없어서 업로드가 실패한다.
- 업로드가 실패하면 워크플로가 실패로 끝난다. GitHub 배포는 이미 끝난 상태이므로, 원인을 고치고 결과물의 AAB 를 손으로 올리면 된다.

### 그 밖에 Play Console 에 적는 것

- 개인정보처리방침 주소: `https://github.com/ldg030201/dong-budget/blob/main/docs/privacy.md` (앱의 설정 > 앱 정보에서도 연다)
- 개인정보처리방침의 개발자 이름(읻옥언)은 Play Console 의 개발자 표시 이름과 맞춘다.
- 데이터 보안: 앱이 개발자나 다른 곳으로 보내는 데이터가 없다(자세한 내용은 개인정보처리방침).

## 처음 설치하는 사람 안내

아래는 GitHub 에서 APK 를 받아 설치하는 경우다.
Play 내부 테스트로 설치한 사람은 스토어에서 받은 앱이라 4번(배터리 최적화)만 하면 된다.

스토어를 거치지 않고 APK 를 직접 설치하므로 최초 한 번 설정이 필요하다.
두 번째부터는 앱 안에서 확인 → 설치 두 번만 누르면 된다.

1. **(갤럭시)** 설정 → 보안 및 개인정보 보호 → **자동 차단 끄기**
   켜져 있으면 스토어 밖 설치가 아예 막힌다. 예외 설정이 없어서 전역으로 꺼야 한다.
2. 브라우저에서 APK 를 받고 **알 수 없는 출처 설치를 허용**한다.
   Play Protect 경고가 뜨면 무시하고 설치한다.
3. 설정 → 앱 → 동계부 → 우측 상단 메뉴 → **제한된 설정 허용**
   이걸 하지 않으면 나중에 알림 접근 권한을 켤 수 없다 (토글이 회색으로 죽어 있다).
4. 배터리 최적화에서 동계부를 **제외**한다.
5. 앱에 **설치 권한을 허용**한다. 앱 안에서 업데이트를 받으려면 필요하다.

알림 접근 권한은 토스 알림 읽기 기능을 만든 뒤에 안내한다.
